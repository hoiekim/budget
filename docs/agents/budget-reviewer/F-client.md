# §F.client — Client / React / UI / calc

Load when the diff touches `src/client/**`, `common/models/**`, or any user-facing rendered surface / client-side calculation.

- **Capacity / budget calculation invariants** — capacity changes are high-blast-radius.
- **Aggregating a TIME-VERSIONED collection into a POINT-IN-TIME bucket — sum the ACTIVE version once, never all versions** — flag any loop that iterates every element of a versioned capacity array (`section.capacities.forEach` / `category.capacities.forEach`, or any `X.capacities`/`X.versions` collection with per-element `active_from`) and `+=`'s each into a bucket keyed by `parent.getActiveCapacity(element.active_from).id`. When the child has MORE version boundaries than the parent, ≥2 child versions resolve to the SAME parent-capacity bucket and their amounts SUM — over-counting every superseded (stale) version. The bucket is then read point-in-time by a consumer (`BudgetDonut` reads `capacityData.get(capacity.id).children_total` / `grand_children_total` for the budget's *currently-active* capacity and shows it as the synced center number / +/- diff / donut fill), so the aggregate contradicts the point-in-time-correct child slices computed right beside it (`child.getActiveAmount(date)`). This is exactly `getCapacityData` (`calculation/budgets.ts:243-265` sections, `:267-287` categories) — budget #590 (2026-07-04, daily-user-testing). Reachable via `CapacitiesInput.onClickAdd` (`index.tsx:124-155`) which appends a period to the CURRENT `budgetLike` only, no parent propagation — versioning a section/category more granularly than its parent triggers it. Correct shape: make the aggregate point-in-time — for each parent capacity period `D`, sum each child's `getActiveCapacity(D)`/`getActiveAmount(D,"month")` ONCE (mirroring the donut's own child slices), not one `+=` per child version. Tests miss it when every child has a single capacity version (`budgets.test.ts:271-327` all use `capacities:[{month:X}]`) — a regression test needs a child with 2 versions under a 1-version parent. Not user-state: base+override periods are correct input; the code mis-sums distinct TIME versions into one POINT-IN-TIME total.
- **Transfers calc-exclusion semantics** — confirmed transfer pairs (`data.confirmedTransferByTransactionId`) are EXCLUDED from `getBudgetData` (spent/income rollups) and `getSankeyData` (Flow chart income/expense), because both halves are internal movement, not real flow. They are KEPT in `getBalanceData` because per-account historical balance must reflect that the account's dollars actually moved. Any PR that flips this asymmetry — passes the map to balance, drops it from budget/sankey, etc. — is a real regression. The split guard in `getBudgetData`'s `splitTransactions.forEach` must use `st.transaction_id` (the PARENT's id), not the synthetic transaction's id, because `SplitTransaction.toTransaction()` overwrites `transaction_id` with the split's own id.
- **Investment transactions are NOT cash flow (Sankey)** — `getSankeyData` / `FlowChartRow/lib.ts` must skip `investment_transactions` of every type unconditionally. A Buy is a position-allocation inside the brokerage (already-arrived cash → securities); a Sell is the inverse (securities → brokerage cash sub-balance). Neither moves money across the household perimeter. The actual household cash-flow event is the **cash-side wire** (a regular `transactions` row on the funding cash account), already counted by Sankey under whatever budget the user labeled it. Flag any diff that re-adds an invest-side branch to `getSankeyData` or any cash-flow calc — the correct shape is `if (isInvestment) return` at the top of `processTransaction` (PR #565). Don't get confused by "double-counting" framing — The maintainer 2026-06-28: *"The cash transaction from the cash account to investment account is recorded in the cash account but not in the investment account. So it's not exactly accurate to say 'double-counted'. The real data quality issue is just missing one part of the transaction."* The cash-side wire and the invest-side Buy are two distinct events; the bug isn't duplication, it's that the Buy was being treated as cash flow when it isn't.
- **Investment cash-flow sign convention (MWR / benchmark only)** — for `benchmark.ts` (money-weighted return), invest txns ARE inputs because MWR measures contribution timing, not household cash flow. There the rule is: (1) count ONLY `Buy`/`Sell` and skip every other type (`cash`/`fee`/`dividend`/`transfer`) — a `transfer` row carries a nonzero `price * quantity` and will silently inflate the contribution column if not skipped; (2) derive polarity from `t.type` (`type === Buy ? +Math.abs(price*qty) : -Math.abs(price*qty)`), NOT from the stored sign of `quantity` — Plaid can emit a sign-flipped quantity. The reference is `src/client/lib/hooks/calculation/benchmark.ts:98` (`type !== Buy && type !== Sell → return`). Flag any MWR-style invest code that trusts the raw `quantity` sign or that collapses non-buy/sell into a contribution bucket (PR #514 shipped both bugs in succession). **Do NOT apply this rule to `getSankeyData`** — see the preceding bullet; Sankey skips invest entirely.
- **DOM measure / `scrollIntoView` right after `setState` reads stale layout** — React hasn't committed the state change yet, so the element being measured/scrolled is still at its old (often zero-height/empty) geometry. `SectionBar.openCategory` called `scrollIntoView({block:'center'})` synchronously after `setIsOpen(true)`, centering a 0-height children div → the section landed mid-viewport, read as "page scrolled away" (PR #568). Flag any `scrollIntoView` / `getBoundingClientRect` / `scrollHeight` read in the same tick as a `setState`. Correct shape: move it to a `useEffect([theStateDep])` so it runs post-commit, target the stable outer ref with `block:'start'`, and gate re-mount auto-runs (e.g. a `pendingScroll` ref) so a reload that restores `isOpen=true` from persisted state doesn't auto-scroll.
- **Scroll bugs are viewport-CONDITIONAL — the scroll container differs by width** — on budget, `<main>` is the scroll container on wide-screen but `<html>`/`window` is on narrow, so `window.scrollTo`/router rAF scroll-restore is a no-op on wide and load-bearing on narrow. A scroll fix (or its E2E) validated only on the default wide viewport can leave the narrow/mobile bug fully present. This is exactly why #568 "fixed" it on wide while the router `scrollTo(0,0)` rAF race was the whole bug on mobile (→ #581 `skipScrollRestore` on same-path nav), and why even after that the auto-scroll overshot the section title off-screen. When reviewing any scroll/layout PR: (a) require the E2E to run on the reported viewport (narrow phone aspect, not just default), and (b) require the acceptance assertion to be the human-visible end state (title fully on-screen: `titleRect.top>=0 && titleRect.bottom<=vh`), NOT a scroll-trajectory metric like "moved toward top / stops N px short." The desired auto-scroll semantic the maintainer specified (2026-07-02): scroll ONLY when the unfolded content is off-screen, and only by the minimum needed to reveal it (if hidden below the fold, scroll up just enough that the content bottom reaches the viewport bottom) — never a fixed scroll-to-top.
- **Scroll/layout PRs must enumerate every fixed/sticky element AND trace every scroll event, not just the intended one** — PR #584 (SectionBar unfold) went four rounds because each round chased the intended scroll but missed a second-order artifact. The failure modes I need to flag on any scroll/layout PR:
  1. **Missing a fixed clip.** Top header (`.Header > .viewController`, 50px) AND bottom nav (`.Header > .navigators`, ~65-80px on narrow — becomes a side rail on wide, no bottom clip). Grep `position: fixed` / `position: sticky` in the touched routes' CSS, list every clip, subtract EACH from `innerHeight` when computing "effective visible viewport." Missing the bottom nav = content lands behind it, "still hidden" is exactly what the maintainer reported on round 2.
  2. **Serial (not parallel) scroll animation.** `window.scrollBy({behavior:"smooth"})` fired after a `setTimeout(300ms)` produces a serial "unfold → then scroll" that reads as janky. The native smooth API also clamps to `docHeight − innerHeight` at animation-START time, so it can't reach past docs that are still growing — the tail is unreachable. Correct shape is a rAF loop over 300ms (matching `.children.transition`) that re-issues `scrollTo(target)` per frame; the browser's per-frame clamp naturally makes progress as docHeight grows.
  3. **Ignoring browser scroll-anchoring.** When an unfold swaps `.LabeledBar` (~48px) for a shorter `.openLabel` (~39px), the browser nudges scrollTop upward by the delta to keep content-below stable — this reads as a spurious "screen scrolls up a little" before the intended scroll runs. Fix is `overflow-anchor: none` on `body` (the scroll container). Flag any scroll/layout PR whose diff swaps sibling elements of different heights AND doesn't opt out of anchoring.
  4. **"Only the top two" (asymmetric report).** When the reporter names a specific subset ("only the top two sections", "only after login"), the fix that ignores the asymmetry is a partial fix. Trace it: for scroll bugs it's often the **max-scroll clamp** — sections whose natural doc-y ≤ `docHeight − innerHeight` can be scrolled all the way to y=0 (under the fixed header, title hidden); sections with doc-y > max-scroll get clamped short, title remains visible. Whoever's reviewing should ask "why THIS subset?" and require the fix to name the mechanism, not paper over the observed cases.
  E2E for these PRs must (a) run on the reported viewport, (b) trace every scroll event over the whole interaction (rAF loop recording `scrollTop` per frame — a monotonic curve is good; `y: 395 → 380 → 404` up-then-down means an anchor jump slipped through), (c) assert `titleVisible = rect.top >= headerH` AND `bottomContentFits = rect.bottom <= innerHeight - bottomNavH` as the pass criteria, not scroll-delta numbers.
- **Dead UI path — an affordance gated behind a prop no caller sets, and an E2E that reaches a surface only by direct URL** — flag any interactive control (kebab, button, editable field block) gated behind a prop with a falsy default when NO caller in the diff (or codebase) sets it truthy: the surface behind it is unreachable in the real UI, so any "it works" claim about it is untested. This is exactly budget PR #587/#588 (2026-07-04): `InvestmentTransactionRow.onClickKebab` — the only navigator to the inv-tx detail page — sat behind `isEditable={true}` with a `false` default no caller set, so the detail page had no live UI path; the manual-tx PR forgot to flip it, and the "UI-driven" E2E actually used `page.goto("/transaction-detail?investment_transaction_id=…")` to reach it. When reviewing a PR whose test plan claims UI-driven verification of a surface, require the plan to name the click path (row → kebab/button → navigation), and treat any `page.goto(<detail/edit URL>)` in the E2E as NOT UI verification for that surface — the affordance must be wired and clicked, or the surface reported unreachable.
- **Text-assertion / measurement-only E2E is NOT visual verification — a UI PR's test plan must include a mobile-viewport screenshot the author actually LOOKED at** — flag any UI-touching PR whose test plan proves only string content (`type === "sell"`), persisted values (`price === 100`), or a `getBoundingClientRect`/computed-style measurement grid, with no screenshot at the maintainer's reported viewport (~390×844 iOS Safari) that a human eye-checked. Layout, formatting, and affordance are DISTINCT dimensions text/measurement can't reach: a grep for "Buy" passes whether the text sits at pixel 30 or 200; a `price===100` check passes whether the input shows `$ 100.00` or a bare `0`; an `input.count()>0` check passes whether the input is visually distinguishable from a read-only span. And `getBoundingClientRect` measures CONTAINERS, not glyph positions — an inline-block input can leave 30px of whitespace between `0` and `$` inside a container whose box still ends uniformly, so the grid reads green while the render is visibly broken. Require the test plan to: screenshot at ~390×844, Read/eye-check it, describe what's literally visible ("Price row: `0` at ~315px, `$` at ~345px, 30px gap"), and — when measurement passes but the render looks off — TRUST the render. Budget PR #588 (2026-07-05) shipped three visible layout bugs (Subtype select left-aligned vs Type right-aligned, bare `0` price with no `$` prefix, no editable-vs-readonly affordance) past a 115/115 text-assertion sweep; the maintainer: *"I think you are not doing visual testing…"*
- **Client call must be typed against the route's real request/response shape** — flag a `fetch`/mutation whose body object or response read is hand-rolled (`{ ticker: raw }`, `body.security`) rather than typed off the route's published request/response type from the server barrel. budget #588 shipped a broken ticker input because the client sent `{ ticker }` where `post-validate-ticker.ts` expects `{ ticker_symbol }` and returns `{ valid, security?, message? }` wrapped, and a catch-all else relabeled the validation error as "Invalid ticker." Require: (a) the call annotated with the imported route type, (b) branching on the specific failure discriminant, not a catch-all else that relabels every non-2xx as one domain error.
- **Aggregation loop over a "touched" accumulator silently skips zero-activity entities** — flag any loop that iterates a Map/dict built up by a *data pass* (`budgetData.forEach`, `valueByX.forEach`, anything seeded only when a transaction/row touched it) and then performs per-entity accrual/derivation that should run for EVERY configured entity, not just touched ones. The rollover accrual at `calculation/budgets.ts:197` does `budgetData.forEach(...)` to walk capacity carry per month — but `budgetData` only holds budget-likes a confirmed transaction touched, so a rollover-enabled budget/section/category with zero confirmed txns is skipped and its "+ X rolled" renders 0 instead of the accumulated unspent capacity (budget #545). Two identically-configured rollover rows then diverge purely on whether one has ≥1 confirmed txn. When the per-entity derivation depends on CONFIG (capacity, roll_over_start_date) rather than on the touched rows, drive the loop over the union of all configured entities (`budgets`+`sections`+`categories`), not over the touched accumulator's keys. (Note: `processTransaction` only credits a category bucket when `category_confidence===1 && category_id`; unconfirmed txns hit the parent budget's unsorted bucket, so "has transactions" ≠ "is in budgetData" at the category/section level.)
- **UI placement change must not tighten gating** — when a diff moves a control (toggle, button, row) INTO an existing conditional block, the block's outer gate (`!isManualAccount`, `isOwner`, feature flag, etc.) silently becomes the moved control's gate too. If the control was previously visible in states the new gate excludes, flag MED: any pre-existing entity in that state is now orphaned — the row may still render in lists (it's still in the data set) but the detail-page control to toggle the state OFF is gone. Safe shapes: (a) lift the row out of the outer gate while keeping it visually adjacent; (b) gate the moved row on `(outerCondition || currentState)` so an entity already in the state can still toggle out. Budget PR #559 archived-on-manual was the recent case (the maintainer, 2026-06-25). Always: when reviewing a placement change, name what states were reachable before and confirm they're still reachable after.
- **Optional visual prop must render conditionally** — when a row component accepts an optional `color` / `icon` / `badge` prop and the rendered DOM contains an element styled by it (`<div className="colorTag" style={{ backgroundColor: color }}/>`), the element MUST be wrapped in `{prop && <div…>}`. An empty `<div style={{backgroundColor: undefined}}/>` still takes layout space and reads as indentation — exactly the maintainer's complaint on `AccountRow` for archived/hidden rows (PR #559). Flag any diff that renders a styled decorator unconditionally when the value driver is optional.
- **Composability of overlapping boolean toggles** — when a PR adds a second boolean control to an entity that already has a related one (Hide/Archive, Mute/Snooze, Disable/Pause), the dependent one must `disabled={dominantBoolean}` so its row can't fire mutations whose effect is invisible. Hide already removes the row from the page entirely; toggling Archive on top adds nothing visible (the row's already gone) and creates a confusing "Show archived (N)" entry. PR #559 Archive disabled-when-Hidden. Flag any diff that ships overlapping toggles without an explicit precedence + disabled wiring.
- **Sibling display quantities must come from ONE cohesive method, not parallel ad-hoc flows** — when a component/hook pulls several related figures for the same entity (a budget bar's `sorted_amount` / `unsorted_amount` / `rolled_over_amount`, an account's balance/change/projection, etc.) and a diff derives ONE of them through a separate inline flow while the siblings come from a shared object, flag MED. The maintainer's standard (PR #563, r3483284677): the figures should be produced together by a self-documenting method on the owning type so the call site reads as one line — `const { sorted_amount, unsorted_amount, rolled_over_amount } = budgetData.get(barData.id).getView(viewDate)` ("See how the code explains itself"). The smell is the asymmetry: one quantity branches off on its own path. The fix is to fold it into the entity's view method (`BudgetData`/`BudgetHistory` `.getView(viewDate)`), not to add a parallel computation at the call site. Same family as the "extend Table.query, don't bypass it" reflex — own/widen the abstraction.
- **Absence of a UI affordance is the signal — flag redundant "excluded"/"N/A" labels** — when a diff adds an explicit badge/label saying an entity is excluded / not-applicable (e.g. "excluded from budget totals" on transfer rows), and that entity type already renders WITHOUT the section other types render WITH (transfers have no budget/category section), the label is redundant UI clutter — flag it. The maintainer, PR #569, r3487698556: *"Don't do this. It just makes the UI busy… That's already an indication that transfers don't have budget / category label."* AND check the inverse: that exclusion is actually honored in the FILTER predicates. Confirmed transfers must be excluded when filtering transactions by a specific budget/section/category, AND excluded from the expenses/deposits page-title filter. A diff that adds the visual label but leaves transfers leaking into those filters fixed the wrong thing — flag the missing predicate as the real bug.
- **Synthetic/system-reserved picker entries: reuse rendered-UI vocabulary, italicize, share the sentinel constant** — when a diff adds a pseudo-toggle/option standing for "items with no label" (an unsorted/none bucket), flag it if it (a) invents a new word ("un-budgeted") instead of reusing the term the chart/list already renders for that case (the Sankey shows budget-less txns as **"Others"**, `lib.ts:82`); (b) renders identically to real user entries instead of visually distinct (the maintainer wanted it *italic* "so users know it's a system-reserved thing"); or (c) hardcodes the sentinel string in two places instead of importing one shared constant (`UNSORTED_BUDGET_ID = "Unknown"` from `common/models/Chart.ts`, used by BOTH the calc fallback and the UI). PR #570.
- **A collection filter must reach EVERY surface derived from that collection, not just the primary list** — when a diff adds a filter over a page's collection (accounts, transactions, budgets…), flag MED unless the filter predicate (or the filtered array) is threaded into ALL consumers of that collection, not only the main row list: sub-lists (Credit / Archived / Hidden built directly from `useAppContext().accounts`), summary/aggregate tiles (the "credit sum" next to the donut), pagination slices, and the donut/chart center. budget #614 (2026-07-08/09) shipped a filter that narrowed only `filteredAccounts`; the maintainer's sandbox E2E found three separate scope-misses in a row — sub-lists still showed credit accounts under a "depository" filter, the credit-summary tile didn't update, and prev/next pagination ignored the filter. `grep` every read of the filtered collection in the page + its children and confirm each respects the filter; require the E2E to exercise the filter against every derived surface, not just "does the main list narrow."
- **URL-param-derived state must be transition-aware — read via the router's `getActiveParams(targetPath)` / pass `targetPath` to the param hook, never raw `router.params`** — flag any new hook/component that derives page/filter state directly from `router.params`. On narrow-screen slide transitions, `path` + `params` STILL hold the OUTGOING route (deferred behind the `setTimeout` in `endTransition`); `incomingPath` + `incomingParams` hold the DESTINATION. So a state read off raw `params` flashes the wrong value during the slide (the maintainer, #614: *"selectedTypes should be read from params or incomingParams conditionally. See other pages for the detail."*). Correct shape post-refactor `1a07bc0e`: the router owns transition-awareness (`useRouter(screenType)` + `getActiveParams(targetPath)` + pure `deriveActiveParams(...)`), and `useMultiSelectQueryFilter(paramKey, labels, targetPath)` reads transition-aware internally; the WRITER always writes through live `params` (a toggle mid-transition updates the real URL, not the outgoing snapshot). Also see section J. When reviewing JSDoc/docs on this path, verify the state model against `router.ts` — claoie's first `getActiveParams` doc INVERTED which of `params`/`incomingParams` is outgoing vs destination and had to be corrected in #617.
- **Table column added → mobile width + full-width empty-state placeholder** — when a diff adds/removes a `<th>`/`<td>` column in a data table, flag MED unless (a) the mobile layout still reads (a new column that makes the first column unreadable on narrow screens isn't worth it — the maintainer had claoie REMOVE the added "%" column on holdings, PR #544), and (b) any empty/loading placeholder row uses `<td colSpan={columnCount}>` so it merges across all columns, never a bare `<td>` that truncates inside column 1. The maintainer, #544: *"the placeholder 'No holdings recorded' should take all columns, as if the whole row is merged."*
- **New modal/overlay MUST lock body scroll on mount** — flag any new modal/dialog/overlay component that doesn't set `overflow: hidden` on BOTH `<html>` and `<body>` on mount (restore prior values on unmount). On budget `<html>` is the scroll root, so body-only locking is insufficient. The maintainer, #624 (2026-07-09): *"UI bug: I can scroll the page while the modal is open. This should be prevented."* Require the E2E to verify the lock with a real `wheel` event (`page.mouse.wheel(0, 400)` → assert `scrollY` unchanged), NOT `window.scrollTo` — scrollTo BYPASSES `overflow: hidden` and false-passes. Same baseline-quality family as dark-theme-match + z-index-above-everything for any new visible surface.
- **UI glyphs use the SVG icon set (`Icons.tsx`), never ASCII/Unicode symbols** — flag any new UI affordance rendering `◀ ▶ ✕ ‹ › ×` or similar ASCII/Unicode glyphs as text; budget has a Font Awesome-based `Icons.tsx` (chevrons, xmark/CloseIcon, etc.). The maintainer, #624: *"Change the ascii symbols with the svg icons. There's a file that has all available icons. It's got chevron icons and probably the x icon too."* Add a new icon to `Icons.tsx` following its existing pattern if one is missing, rather than falling back to a text glyph.
- **"Current / live / default" view state = ABSENCE of the query param, not the param written to its current value** — flag any "Today/Current/Reset/All" affordance that does `params.set(key, currentValue)` instead of `params.delete(key)`. Setting `?view_date=2026-07` when the user clicks Current freezes a bookmark to July; deleting the param keeps it live. Navigation that carries the state forward (`router.go` preserving `view_date`) copies the param ONLY when present — an absent param means "live" and injecting the resolved value silently pins it. The maintainer, #624: *"When [current] button is clicked, remove the view date param. This is different from setting the param as current month string. It's useful for bookmarks."*
- **Account-snapshot writes: send the BARE `YYYY-MM-DD` to `POST /api/snapshot`, never an ISO `…T00:00:00Z` string.** The route derives `snapshot_id = ${account_id}-${getSquashedDateString(new LocalDate(date))}` in **server-local (PST) time**; `LocalDate` reads a bare `YYYY-MM-DD` as local midnight (id lands on the picked day) but reads an ISO `…Z` in UTC → local-tz shifts it BACK a day → the stored id/date is off by one. Flag any account-snapshot POST that passes `new Date(input).toISOString()` for `snapshot.date` (or defaults a date input via UTC `toISOString().split("T")[0]` on a local Date, which pre-fills next month in PST). Render/default snapshot dates with `getDateString` (local), not the UTC slice. budget #632 (2026-07-11).
- **A CSS claim must be measured against the RUNNING BUILD, not a hand-rebuilt fixture — and budget sets `* { box-sizing: border-box }` globally.** Rebuilding a component's DOM in headless Chromium with only the one stylesheet under review drops `App/index.css:1`, so every element silently reverts to content-box and any `min-height` / `height` / `width` arithmetic that interacts with padding comes out wrong. budget #693 (2026-08-09): the review argued `min-height: 16px` on a padded label was the 44px tap-target floor (`16 + 14 + 14`) and measured 44px-with vs 37px-without in a fixture — on the real build it measured 38 vs 38, i.e. the declaration was **inert**, because under border-box a 16px min-height sits under 28px of padding. Run the app and measure there; a running build of any branch that does not touch client code is a valid CSS baseline for `main`. Related: when reasoning about a **selector**-scope change, note that combinators contribute nothing to specificity — relaxing `A > B > C` to `A > B C` leaves specificity unchanged, so it can only newly beat rules on elements it did not previously match, which is a tighter blast-radius argument than enumerating screens.
- **A shell/primitive whose layout is bound to a direct-child chain silently un-styles any consumer that interposes a wrapper — enumerate wrappers by grepping the class producers, not by walking screens.** `Properties/index.css` binds the section frame to `div.Properties > .property`; the row box was likewise `> div.property > div.row` until #693. Flag any new direct-child layout rule on a shared primitive, and when reviewing a change to one, find the complete consumer set structurally: grep for every producer of the class (in budget: `Properties/index.tsx`'s `Row`/`KeyValue`/`ButtonRow` and `RadioInputs.tsx`'s `option row`), then read every call site for an interposed node. A screen-by-screen E2E sweep cannot prove exhaustiveness — #693's first pass walked five screens and missed the `<form>` wrapper in `HoldingProperties`'s `isNew` branch. The tell that a wrapper site is a *bug* rather than a choice: site-local CSS compensating for the missing shell rule (a hand-rolled `padding` on a `.row`), or a comment asserting the shell rules "cascade" when only the descendant ones do.

- **`Comparable.format` (`lib/hooks/sorter.ts`) silently zeroes a mismatched pair — so a sort formatter's fallback turns a falsy value into an invisible ordering drop-out, not a visible mis-sort.** It only accepts number/number, string/string or Date/Date; anything else sets `a = b = 0` and the rows tie. Flag any `sort`/`useSorter` formatter arm shaped `return e[key] || e.id` (or any `|| <string>` fallback) on a key whose real value can be `0` / `""` / `null`: a zero-amount row then hands the comparator a string, ties against every numeric sibling, and lands wherever the stable sort leaves it. budget #676 / PR #702 (2026-08-12): the investment arm's generic tail did exactly this to the zero-amount manual mints the filter deliberately keeps visible. Ask of every formatter arm: *what does this return when the field is falsy, and is that the same TYPE as the other rows return?*
- **`useSorter.sort` applies each `sortings` entry in Map order and `Array.sort` is stable, so the LAST entry is the primary key** — earlier entries survive only as tiebreaks. Reading the map left-to-right gives the wrong mental model; a review that reasons about "the first sorting" is reasoning about the weakest one.
- **Resetting state during render must key off `useState`, never `useRef` — budget runs `React.StrictMode` on a concurrent `createRoot` (`start.tsx`).** The pattern (`if (prev !== next) { setPrev(next); setDerived(...) }`) is correct and preferable to a `useEffect` resync, which paints the stale value for a frame. But a *ref* guard survives a render React abandons while the queued state update does not — so the ref reads "already handled" for a render that never committed and the resync never happens again for the life of the mount, converting a transient staleness bug into a permanent one. Flag any `useRef`-guarded render-phase reset. budget PR #702 (2026-08-12), `useLocalStorageState`.
- **A hook whose storage/memo key is derived from props or route state must re-read when that key changes.** `useState(() => read(key))` runs its initializer once; if the component stays mounted across a key change (same route, different params) it serves the previous key's value AND the next write persists it into the new slot. Flag any `useLocalStorageState` / `useMemoryState` / cache-hook call whose key is a template literal or a computed string, then check what guarantees a remount — usually a React `key` on the component, sometimes an early-return in an unrelated navigator. If the remount argument lives in a different file, say so: it is load-bearing and invisible. budget #676 / PR #702: `TransactionsPage`'s `sortKey` changes on a mounted page via both the account filter and the type-filter dropdown.
- **A header/control that cannot affect its view is dead UI — require it removed or the PR to say it is inert.** When a list view is structurally scoped to one value (e.g. `TransactionsPage`'s investment branch is only reachable with an `account_id` filter, so every row shares an account), a sort header on that column formats identically for every row, the comparator is all zeroes, and clicking it moves its own arrow and nothing else. Flag the header set, not just the sort code — a PR that fixes "the sort buttons do nothing" while leaving one that still can't work has closed the issue partially. budget PR #702 dropped `account` from the investment header set for exactly this reason.

- **A fallback price/date lookup silently redefines the window — the label and every co-plotted series must move with it.** TWR telescopes to `priceAt(windowEnd) / priceAt(windowStart) − 1`, so when `priceAt(requestedWindowStart)` falls back (stale-forward to a prior txn, or pre-history to `arr[0]`), the account's *effective* start becomes the fallback's source date while the widget label and the benchmark side still use the *requested* date — two returns measured over different windows, compared as if they weren't. budget 653 → 700 (2026-08-12). Flag any metric code where a lookup has a fallback arm and the resolved date is not fed back into (a) the window bounds used by every other series in the same comparison and (b) the user-visible label. Generalize past prices: any `find`/`at`/nearest-match with a fallback inside a windowed calculation.
- **A domain predicate defined as a local lambda in a page/filter module, when the model class already exposes a method over the same fields, is a defect waiting to happen — flag it even when the diff didn't introduce it.** The shape: `const isUserLabelConfirmed = (e) => { const c_id = e.label.category_id; const c_conf = e.label.category_confidence; return !!(c_id && (c_conf === 1 || c_conf === 0)); }` in `src/client/pages/TransactionsPage/filter.ts:24-28`, while `src/client/lib/models/Transaction.ts:46` owns `isConfirmed(): category_confidence === 1 && !!category_id` and `src/client/lib/hooks/calculation/budgets.ts:86-89` calls it. The two predicates disagree on exactly one row class (`category_id` set, `confidence === 0`), which is how budget shipped a "see 1 unsorted…" button that navigated to an empty list while the count said 1 — one concept, two implementations, divergent since `77e03c70` (2026-05-27) and only found when the maintainer hit it 2026-08-17.
