# §F.sync — Plaid / SimpleFin / delta sync / SSE / cache

Load when the diff touches `src/server/lib/plaid/**`, `src/server/lib/hooks/sync.ts`, SSE/realtime plumbing, cache layers, or Plaid entity reconciliation.

- **Chatty endpoints that fan out to a shared, globally-cooled-down side channel** — `sendAlarm` (`lib/alarm.ts`) is cooled down **per key** plus a global `MAX_SENDS_PER_WINDOW` ceiling, and `/api/client-error` must pass its own bucket (`sendAlarm(title, detail, "client-error")`). Flag any diff that reverts the `Map<string, number>` back to a single `let lastAlarmAt`, that drops the global ceiling (per-key alone is unbounded — `Route.execute` keys on the registered path, so a broad outage gives each of ~55 routes its own eligible bucket), that spends a key's cooldown on a send the ceiling refused, or that adds a new high-volume route calling `sendAlarm` on the default (title) bucket. With one shared bucket, one request per minute to the beacon endpoint suppressed the ENTIRE server-side alerting surface — route 5xx (`lib/route.ts:91`), `uncaughtException`/`unhandledRejection` (`start.ts:471/479`), scheduled Plaid/SimpleFin sync failures (`compute-tools/schedule.ts:36,49,81,112`), Item Bad Status (`plaid/transactions.ts:72,177`, `plaid/accounts.ts:37,109`). Filed as budget #663, part 1 in PR #664.
  🔴 **CORRECTION (2026-07-30) — `/api/client-error` is NOT unauthenticated.** A prior version of this bullet said `/health` and `/client-error` were "the only two intentionally guard-free routes." That is false and it propagated into PR #664's threat model, three source files and the PR body before review caught it. Ground truth: `PUBLIC_PATH_METHODS` (`start.ts:185-189`) contains **only** `/login`, `POST /plaid-hook`, `GET /health`; `start.ts:337` returns 401 for any other path without `session.user`. Verified empirically (anonymous `POST /api/client-error` → `401 Not authenticated.`). So the alarm-suppression bug is a noisy-neighbour / self-inflicted-retry-loop problem needing a valid session, **not** an anonymous-internet DoS. Always re-derive a route's auth posture from `PUBLIC_PATH_METHODS` + the `start.ts` gate before asserting it in a review or a PR body — do not trust this file or a PR's own framing.
  Corollary: a client error thrown *before* login beacons into a 401 and is silently dropped — a real, still-open functional gap, not the security hole #663 describes. And "rate limit this route per IP" (#663 part 2) buys little against an already session-gated route; the residual hole is client-vs-client (one report/min owns the shared `client-error` bucket) and its fix is a per-error-fingerprint key, which is when caller-influenced keys make the expired-entry prune load-bearing. Related: `lib/rate-limit.ts` still only exposes login-specific helpers, so any "rate limit this route" claim needs a real (bucket, IP) limiter, not a copy of the login logic.
- **`min(loaded.date)` is not history depth under a delta sync** — flag any client calc that infers "how far back do I have history" from the oldest *date* among loaded transactions. The sync engine keys its delta window on `updated` (last-edited cursor), so a single back-edited 5-year-old row lands in the recent fetch and drags `min(date)` back years while only sparse old rows are present. Accruing per-month capacity from `min(date) → now` over-accrues. The correct completeness signal is the sync-state flag `isColdSync` on `Status`: while `isColdSync`, skip the history-dependent accrual entirely; compute it only after the unbounded Stage 4 fetch commits. Cursor key (`updated`) and reasoned-about field (`date`) are different axes — never infer dataset completeness from a property of the rows you happen to hold. (budget #509.)
- **Realtime `<table>-updated` handler syncs ONLY the affected domain, not a full `sync()`** — when a client receives a per-domain realtime event (SSE/WS `<table>-updated`) and reacts by re-fetching, flag any handler that fires the whole `sync()` (all tables) instead of a scoped `syncDomain(table)`. A full sync on every mutation-notification defeats the point of a targeted push and multiplies fetch cost by the number of connected tabs × domains. The maintainer, budget #658 (2026-07-27, real-time collab PR 2/3, on `Utility.tsx`): *"Does this sync all data? Shouldn't we sync specific table only?"* → resolved by `useSync` returning a domain-scoped `syncDomain`. Same asymptotic-cost lens as the batch-not-loop rule; here the axis is "sync the delta the event names, not everything."
- **Plaid stays the source of truth — reconcile duplicate/mismatched entities by remapping YOUR canonical DB rows (with full FK cascade), never by mutating the incoming Plaid payload.** Flag any `sync-plaid`/holdings/securities diff that rewrites, dedupes, or "fixes" the *incoming* provider data before persisting it — Plaid is authoritative, so an inbound edit gets clobbered on the next sync and fights the provider forever. The correct shape for a duplicate-security collision is a DB-side merge: keep one canonical `securities` row and repoint every table that FK-references the dead `security_id` **in the same transaction** — `investment_transactions`, `holdings`, AND `holding_snapshots` (grep the schema for the column; a merge that updates the parent but leaves any referencing table pointing at the dead id splits the position / orphans history). The maintainer, PR #598 (closed, discussion_r3532663797): *"Let's keep plaid as the source of truth. Can we remap the securities in DB instead of the incoming holdings? When remapping securities make sure to remap investment_transactions and holdings / holding_snapshots that reference that securities."*
- **A realtime / multi-client / collaboration PR is NOT verified until a TWO-client E2E shows one client's mutation rendering in the OTHER — a "refetch fired" assertion proves transport, not the feature.** Flag any SSE/websocket/push/collab PR whose test plan asserts only that a receiver *issued* a refetch (or only a server-side curl matrix / unit tests). Require a two-`browser.newContext()` (or two-tab) Playwright script: drive the mutation via a real UI affordance in client A, then assert client B's **rendered DOM** actually changed (row appears/updates/removes) plus a `pageerror`/console-error watch on B. budget #656 arc (#657/#658/#659, merged 2026-07-26→27) shipped with only a one-tab "asserted `/api/transactions` refetch was issued" check → the maintainer 2026-07-28: *"How did you verify this work? It doesn't seem to be working."* If a happy path needs a signature/secret the sandbox can't mint (e.g. #659's real Plaid JWT), drive the two-tab test on the reachable paths and say so — don't shrink the whole verification to unit tests.
- **A long-lived / streaming response needs an explicit `idleTimeout` on `Bun.serve`, and any keepalive MUST tick well inside it.** `Bun.serve`'s default `idleTimeout` is **10 seconds** (max 255) and `src/server/start.ts` passes none — so any response held open with no bytes flowing is reaped at ~10-12s regardless of the client. Flag HIGH any new SSE/streaming/long-poll route, and any change to an existing one's keepalive interval, unless the keepalive period is provably **less than** the server's idle timeout. budget #669 (2026-07-31): `/api/events` shipped with `SSE_KEEPALIVE_MS = 30_000` against the 10s default, so the keepalive interval could never fire — every subscription died at ~12s (Bun logs `[Bun.serve]: request timed out after 10 seconds. Pass idleTimeout to configure.`), and because `emitToUser` early-returns on an empty subscriber set with no queue/replay/`id:` field, every mutation landing in a reconnect gap was silently lost forever for peer tabs. Pair the review with the two-client E2E rule above; also require the reconnect path to reconcile (re-`sync()` on `EventSource` open) rather than assume the gap was empty, since nothing else on the client re-syncs (no interval, no `visibilitychange`, no focus refetch — `sync()` runs only on the login transition).
- **Never clear a client cache speculatively — the clear sits AFTER the success branch of the fetch that replaces it.** `clear → fetch` shows an empty UI for the whole round-trip and, on fetch failure (network drop, 500, expired session), permanently destroys the only fallback. Correct order: fetch → on-success swap in the new data → then clear/replace the cached copy; on failure keep the cache and surface a sync error (budget 400, the maintainer: *"Clear indexed DB only if network fetch succeeds"*). Flag any `indexedDB.deleteDatabase`/store-clear, `caches.delete`, `localStorage.remove*`, or `setData(null)` that runs before its replacement data has arrived. Carve-out: security-driven wipes (logout, role change) may clear unconditionally, but still after their own confirmation step.
- **A change to the IndexedDB store list without a `DB_VERSION` bump is HIGH — and so is any client reconnect that drops the last event id.** IndexedDB creates stores only in `onupgradeneeded`, which runs only when the requested version exceeds the stored one; a fresh test profile creates every store, so the bug is invisible to E2E unless the profile is pre-seeded with the previous version. PR 947 (2026-10-16) added `StoreName.recurrings` at `DB_VERSION = 5`; every existing browser then threw `NotFoundError` from `loadAllData` and `clearAllData`, every sync ran cold, the failed clear removed the cursor (921's purge rule), and every load/reopen emptied the transaction list and the budget bars until PR 965 bumped to 6. `accessor.test.ts` now pins the store list to the version — require both values updated together, plus `onblocked` (an old tab holds the old version open) and `onversionchange` handling. Sibling, PR 963: `useServerEvents` reconnects by building a new `EventSource`, which carries no `Last-Event-ID`, so every reconnect drew `retry-full` and a whole-app `sync()`; the client must carry the id itself (`?last-event-id=`), and server event ids must not collide across a restart (boot-time counter base).
