# §F.cross-cutting — Always load

Applies to every diff regardless of code area — code hygiene, PII, verification discipline, scale principles, testing gotchas, type/naming rules.

- **Whole-file reformat churn in a scoped PR (prettier)** — flag any diff where files carry large reflow-only hunks (line-wrapping changes, arg lists exploded onto separate lines) unrelated to the PR's stated scope. `hoiekim/budget` does not declare prettier or a `.prettierrc*`, so running it falls back to prettier's **80-column default** and reflows every touched file — budget PR #662's `<ButtonRow>` migration went from 133+/166- to 594+/292- that way, and it also installed prettier + rewrote the lockfile. `eslint` is the only formatter of record; the repo's de-facto width is ~100. A lockfile change in a pure-refactor PR is the tell. Direct hit on the scope rule (no unrelated changes).
- **Don't rebuild a Set from a Map's keys** — `Map<string, X>` already supports `.has(id): boolean`. If a diff materializes `const set = new Set(); map.forEach((_, k) => set.add(k));` only to call `set.has(id)`, that's redundant. Use the Map directly. Calc-function params that take a "do you have this id" lookup should be typed `ReadonlyMap<string, V>` if the value type is meaningful, or structurally `{ has(id: string): boolean }` if it isn't — both make Set OR Map work without a parallel build.
- **`mock.module("../client" | "server" | "client", …)` barrel mocks** — Bun's `mock.module` is process-global and hoists across the whole test run, so mocking a barrel in one file bleeds an unexpected stub into unrelated suites. New tests should NOT mock a barrel — mock the leaf `pg` dependency (FakePool) and run the real code, the `users.test.ts` pattern. Flag any new barrel mock.
- **New status flag: reuse existing / name for the state** — when a diff adds a boolean to `Status` (or any state object), flag it if an existing flag (`isLoading`, `isSyncing`, an existing phase flag) is already true exactly when the new one would be — reuse it. If a new flag is genuinely needed, the name must describe the *state* (`isColdSync`), not a symptom (`isTransactionHistoryPartial` — long, couples to one consumer). The maintainer, #509: *"This is ugly. Why can't you use `isLoading`? If you still need a new flag, how about `isColdSync`?"*
- **Asymptotic cost — no N-round-trip loops** — if the diff has a `for` loop calling `pool.query` / `Table.method` / `await fetch` / `await client.<rpc>` over a per-user collection, flag HIGH. Single batched call (`= ANY($1::text[])`, `IN`, `unnest`, `WITH` CTE, `Promise.all` for genuinely-independent IO) is the default, not a perf-optimization. The reflex of "loop over ids and await each one" is the smell the maintainer pushed back on most recently — PR #541 cascade loop: *"This is not what I suggested. I was asking about the table method `bulkSoftDeleteByColumn`. Why doesn't this method take a list of ids? What is the reason to avoid making it take a list?"* The fix is to widen the Table method itself (per the no-bypass rule above), not to bypass it with raw SQL or a JS loop.
- **Full-fetch read endpoints scale with users** — flag any new `GET /<entities>` route that returns "all of X for the user" with no `?since=<cursor>` filter and no `?include-deleted=true` tombstone mode. Pattern: PR #536 transactions (delta-by-cursor + tombstones), #542 transfers (follow-up). The acceptable transitional shape is "full-fetch route + filed issue to follow-up with delta-sync" — but a NEW endpoint shipping without the pattern is a regression. Indexes for the `updated >= $cursor` access path must be in place.
- **Cron job hot-path multiplies by user count** — `runTransferDetection`, `scheduledSync`, any `for (userId of userIds)` loop. Anything inside that loop multiplies cost by user count. A per-user UPDATE that scans the user's table without an index, a per-user N-round-trip cascade, a per-user JS recompute that should be SQL — all flag at HIGH for engine paths.
- **PII in committed source comments AND commit messages — not just PR/issue text** — a text-leak scanner is usually run on PR bodies, but real-account currency figures, financial-institution names, and account labels also leak via **code comments and the commit-message body**, which ship permanently in public source + git history. PR #565 leaked a six-figure balance / balance deltas / a real bank name / a real account label / "unscrambled prod-clone" in a `FlowChartRow/lib.ts` verification comment, the test-file comment, AND the commit message. Flag HIGH any committed comment or commit-message body that cites a concrete `$NNN,NNN` figure, a real institution name, a real account label, or watchlist tickers — verification narratives must be qualitative ("a spurious deficit reconciling to a surplus modulo manual appreciation"), never with the numbers. Run the leak check on the diff AND `git log -1 --format=%B`, not just the PR body.
- **A real mail address at the operator's own domain is PII, and E2E evidence is where it leaks** — measured 2026-09-18: 25 public artifacts in another project carried a per-service alias roster (`<service>@` local-parts, …) with per-alias mail counts beside it, harvested into PR bodies and issues as evidence against the real mailbox. Every one is a confirmed-deliverable address, and the **set** discloses which services the operator holds accounts with — so this is disclosure even where no single line looks sensitive. The gate had no rule for the operator's own domain until that day, so a diff or PR body can pass the text-leak scanner on an old checkout and still leak. Flag HIGH a non-fixture local-part at the operator's mail domain, and any third party's address at a real external domain, wherever it appears — PR body, issue body, test fixture, committed comment, screenshot alt-text. Fixtures (`admin@`, `test@`, `bob@`, `ut-spam-*@`), bot identities and the published `CODE_OF_CONDUCT.md` contact are allowed; a service name as the local-part is exactly what is not. Scrub to `<alias-N>@<domain>`, stable across artifacts so cross-referencing prose stays coherent. Same reasoning as the currency rule above: the evidence must be qualitative ("the largest mailbox", "an alias with ~700 mails"), never the roster.
- **No duplicate type — reuse an existing `BudgetFamily`-like shape** — flag any new `type`/`interface` whose fields overlap an existing model/union in `common/models/`. The maintainer, PR #563, r3487442310: *"We already have `BudgetFamily` type or something similar… Don't write duplicate code."* Grep the barrels for an existing union/`*View`/`*Summary` type before accepting a new shape; reuse or widen it. Type-level counterpart to the no-bypass / no-thin-wrapper reflexes.
- **Shared `ctx`/`config`/`deps` threaded through a family of functions → capture once in a constructor** — flag any group of ≥2 related functions/predicates/handlers that each take the SAME trailing context argument (`(e, ctx)`, `(row, config)`, plus a free `matchesAnyX(item, types, ctx)` dispatcher). That repeated arg is a constructor dependency in disguise. The maintainer's preferred shape (PR #575, r3496336886, *"Instead of injecting `ctx` in every function calls, I prefer initializing it once and store it as a private property"*): a small class taking the context in its constructor, per-item methods as one-liners reading `this.<field>`, and a single dispatcher method `any(types) => e => types.some(t => this[t](e))` replacing the free helper — call site `new TypePredicates({ transfers }).any(["deposits","unsorted"])`. Tests keep an old `(row, types, ctx)` signature via a thin wrapper that constructs the class. Same family as the extend-the-type / own-one-abstraction reflexes — context belongs to the object, not every call.
- **Renaming a family of symbols → check model-name collision + per-member semantic difference** — flag a blanket rename that drops a suffix across a group of predicates/types when (a) the shortened name could be read as an existing model/type concept (`isTransfer` reads as if there's a `Transfer` model; there's `TransferPair`/`TransferDictionary`, and a transaction isn't the transfer, it's part of one), or (b) the dropped suffix encodes a distinction that DIFFERS across the family. PR #575: render-side `…Half` predicates classify whole transactions that are one half of a pair (keyed on the txn id), while the budget-exclusion predicate keys on `transaction_id` so it also covers a SPLIT of a confirmed-transfer parent — a sibling of the half, not a half — so `…Half` is right for the render ones but wrong for the budget one. Don't accept a uniform rename of a non-uniform family; each name should track what that member actually means. The maintainer: *"Would it confuse the reader to think that transfer means the `Transfer` model? Should we keep the concept of `TransferHalf`?"*
- **Hand-rolled structural type duplicating a domain model → reuse the model (with `Picker`)** — flag any local `type X = { … }` whose fields mirror a subset of an existing model (`Transaction`, `SplitTransaction`, an entity in `common/models/`). PR #575 introduced `type LabeledRow = { label: { category_id?; category_confidence? } }`; the maintainer, r3499317389: *"Can you reuse the Transaction model for this? You can use `Picker` if necessary. \"Don't repeat yourself\" -- prevent drift."* A bespoke shape mirroring model fields drifts silently when the model changes — helpers should take the model type (or `Pick`/`Picker` of it) directly. Sibling to the no-duplicate-type reflex above; this catches the *structural* (inline `{…}`) form of it.
- **Helper param type must match its sibling helpers** — flag a new helper in an existing family whose parameter type differs from the neighbors' (`Transaction | SplitTransaction`) for no stated reason. The maintainer, r3499330919: *"Other functions use `Transaction | SplitTransaction`. Why not consistent?"* Grep the neighbors and match; an ad-hoc narrower/wider type is itself the smell.
- **Parallel free helper beside the class that owns the concept → fold it into a class method** — flag a standalone `function fooForX(item, types)` living next to a class that already owns that concept (e.g. `matchesAnySelectedInvestmentType` beside `TypePredicates`). The maintainer, r3499360323: *"Fold this into `TypePredicate.any` method."* The dispatcher/method on the owning class should absorb the special case (each predicate accepts the full union), not a sibling free function. Same cohesion family as the getView "produce siblings together" rule.
- **Unnecessary backwards-compat carve-out / special-case branch → challenge "is this necessary?"** — flag a special-case branch (a fall-through, an `if (isInvestment) …` short-circuit, a "show everything when only non-X selected" hack) that exists only to preserve an old function's behavior. The maintainer, r3499477045: *"Is this necessary? Wouldn't it work without it?"* — the investment sign-filter carve-out in `TypePredicates.any` was a backwards-compat hack; dropping it (commit `2709081f`) made investment rows correctly fail every non-sign predicate (empty list is the right answer), and the tests pinning the old behavior flipped to `.toBe(false)`. Default to trying the removal and checking whether the tests still read sensibly, rather than justifying the branch. A "refactor for readability/simplicity" that GROWS net non-test lines (the maintainer *"Why did it end up adding even more LOC?"*) is a related smell — check the net line delta on the non-test files.
- **Self-documenting code — flag redundant JSDoc, missing edge-case tests, loose runtime contracts** — every diff's docstrings, tests, and runtime validation must EARN their lines. Three smells:
  1. **JSDoc that restates the function name / signature / implementation.** *Smell:* `/** Checks whether the row is suggested. */ const isSuggested = (e) => e.label.confidence > 0 && e.label.confidence < 1`. *Pass:* one-line intent + a load-bearing *why* (an upstream constraint, a hidden coupling, a past incident the implementation can't show). PR #575 (2026-06-30): ~60 lines of bullet-doc that repeated what each predicate one-liner already showed — the maintainer *"Why did it end up adding even more LOC?"* — trimmed to ~30 lines that kept only the cross-cutting facts.
  2. **Tests skip edge cases the function NAME implies.** *Smell:* `isInConfirmedTransfer` tested only on the happy path (confirmed half → true). *Pass:* tests every case the reader would infer from the name — confirmed half, suggested half, split of confirmed parent, no pair, rejected pair. If a single case is missing, a future refactor can silently flip the semantic. The rule: write the cases the *name* promises, not just the cases the current implementation handles.
  3. **Runtime contract wider than the name implies.** *Smell:* `getActiveBudget(user_id)` whose return type is `Budget | undefined` — the name says the budget exists, the type silently widens. *Pass:* either rename (`findActiveBudget`) or throw on the contract violation at the boundary. Route handlers / queue consumers parse external input to the expected shape and throw on mismatch; internal callers can trust narrow types.
  **Comment hygiene — self-documenting code is the north star. Flag every violation.** Never-in-code list: PR narrative / change history, `#N` / issue / PR refs in source, restated fixed bugs, hex ids or sentinel values from bug logs, attribution by name, comments that restate what a well-named identifier already says. Four narrow exceptions: (1) JSDoc on public/abstraction surfaces where an IDE tooltip earns the space, (2) `TODO` markers, (3) one-line WHY when the *why* isn't derivable from the code (a Postgres/Bun/Plaid quirk, CSS direct-child dependency, race workaround), (4) long external context lives in `docs/*.md`. If a comment answers "would a fresh reader who never saw this PR still need this?" with NO, flag it.
- **A `clone`/copy/factory that `new BaseClass(this) as Subclass` (casts) instead of `new this.constructor(this)` breaks `instanceof` dispatch downstream** — flag any clone/copy method that constructs the BASE type and only *casts* to the concrete subclass. The cast is compile-time only; at runtime the object is the base class, so any downstream `x instanceof SubType` / `switch (x.constructor)` dispatch falls through to its `default: throw` branch (or writes the wrong slot silently). budget #628 (2026-07-11, HIGH): `Dictionary.clone = () => new Dictionary<T>(this) as S` produced a base `Dictionary`, so `Data.set`'s `instanceof ChartDictionary` dispatch threw `Data.set: unknown dictionary Dictionary` INSIDE the `setData` updater (surfaces at React render), breaking every `useMutate` mutation site. Correct shape: `clone = (): S => new (this.constructor as new (init: Iterable<…>) => S)(this)` — subclass-preserving for empty-body subclasses (inherit the base ctor) AND custom-ctor ones (e.g. `TransferDictionary` rebuilds its pivot). It also fixes latent downcasts in any sibling using the same clone (`Dictionary.map()` was silently returning a base instead of its typed `S`). **Verification corollary (E2E):** the mutation's API call (DELETE/POST) fires BEFORE the throwing `setData` updater, so a DB-row-count / API-side-effect E2E (charts 8→7) PASSES while the render throws — a proxy metric masking a render bug. Verify the RENDER: zero console/`pageerror` events + the DOM reflects the change + navigation completed (`router.back()` runs only if the updater didn't throw), never just the side effect.
- **A value read as a proxy for concept X must equal X *by design*, not as a side-effect of where a loop/scan happens to stop** — flag HIGH any code (especially load-bearing budget math in `Calculations.ts` / the accrual loop) that reads a stored/computed quantity as if it carried a named meaning when that quantity only holds that meaning as the *residue of a loop's termination bound*. budget #637 (2026-07-14): a future-month rollover projection seeded `S(T)` (month-T banked spend) by reading `rolled_over(T+1)` from the accrual history — but `rolled_over(T+1)` equals that carry ONLY because the accrual loop's bound is `startDate <= endDate(T)`, so it stops before writing `T+1` and the last-written bucket coincidentally holds it. Move the bound one month and it silently double-counts. The maintainer: *"It's just a side product of the calculation loop. Not intentional… using it in this place to represent `S(T+1)` is fragile."* Correct shapes: (a) make the value authoritative — extend the loop to *intentionally* write the value, so the semantic is stated; or (b) read a semantically-named source that means X by construction. The tell: the value's correctness depends on a loop's `<=`/`<` boundary, not on a definition.
- **File-split refactor must split its TEST file to match — flag a monolithic test alongside decomposed source.** When a PR splits one source file into per-component files (`X.ts` → `X/{a,b,c}.ts`), the test must be partitioned the same way (`X/a.test.ts`, …) in the SAME PR. Cross-repo lesson, the maintainer in another project (2026-07-27): *"Why don't you split mails.test.ts?"* Gotchas when the test moves into the new dir: `await import("./X")` → `await import(".")`, and source-scan guards' `path.join(import.meta.dir, "X")` → `import.meta.dir` + a `.test.ts` readdir filter.
- **Axis / sentinel / normalization at a helper boundary → audit EVERY sibling in the same file for the same gap, and every downstream consumer for a "made-reachable" bug.** When a PR adds a discriminator flag to a helper (`isUidCommand`, `isOwner`, `isAdmin`, `isDraft` — any "which of two axes are we on"), or tightens sentinel/reversal normalization on one range-shaped input, do NOT stop at the touched helper. Grep the same file for every function that takes the same value-type (any `{start, end}` pair, `Range`, `SequenceSet`, `Set<id>`, `Dict<key>`) and check each for the SAME class of gap in the SAME PR. And after every fix commit, ask *what previously-silent code path does this fix newly unmask?* — fixing an upstream counter/predicate that used to skip a gate now fires the gate, which puts control into a downstream branch that may still carry the pre-fix shape (a silent bypass becomes a silent zero-fetch, or a silently-succeeded no-op becomes a visible failure elsewhere). Cross-repo lesson from another project: SIX reviewoie rounds on one class in one file because sibling helpers were fixed one at a time and each fix unmasked the next. Applies wherever budget has sibling helpers on one value-type (`Dictionary` / `ChartDictionary` predicates, `LocalDate` conversions, budget/cash forks in `Calculations.ts`, transfer-pair sort/compare/dedupe siblings).

- **Counting call sites: grep the bare identifier, never `identifier\(`.** `rg 'useLocalStorageState\('` returns 1 hit where the truth is 6 — every generic invocation (`useLocalStorageState<string[]>(`) has the type argument between the identifier and the paren. Any blast-radius claim in a PR body built on an `identifier\(` grep is undercounted; re-run it yourself before accepting it.
- **Reject a root-cause claim in a PR body that doesn't explain the error's SHAPE.** "floating-point precision", "rounding", "price-source divergence" are zero-mean and non-accumulating; if the reported symptom is *directional* or *grows with window width / row count*, those causes are falsified by the symptom itself and the PR is built on a wrong diagnosis. The maintainer ran exactly this falsification twice on 2026-08-12 before the real cause surfaced: *"the diff grows as the window widens. That means the cause is not rendom precision issue. It's directional … Your theory doesn't explain that"* and *"why doesn't it average-out? Why does it accumulate over time?"* Require the body to state what the mechanism predicts about sign and scaling, and to match that against the observed shape.
- **A verification performed on a single-holding / single-security account does not generalize — say what makes the fixture special.** A 100%-one-ETF account is the right *oracle* for return math (TWR must equal the benchmark exactly, so any delta is pure defect), and it is the wrong *sample* for anything data-shaped. The maintainer, same thread: *"(2) doesn't work for other accounts. This account just happened to have only <ETF>. Other accounts are not like that. Yahoo CSV file only exists for <ETF>."* Flag a PR whose evidence section rests on one account without naming the property that account has and the general case doesn't.

- **Any bug whose symptom is "the count and the list disagree" / "the badge and the page disagree" is ONE bug, and the only acceptable fix converges both callers on the model method.** Reject a fix that edits the divergent site's literal to match (`return !!(c_id && c_conf === 1);`) — that leaves a third copy of the predicate and the next divergence is unpreventable. The maintainer's review, verbatim: *"Don't we have a class method for unsorted calculation?"* If the two predicates encode genuinely **different** concepts (here `isConfirmed` = "user confirmed" vs "user acted, confirmed OR rejected"), require BOTH to become named sibling methods on the model (`isConfirmed()` / `isUserActed()`), so the distinction is stated once and each caller picks deliberately — a difference that exists only as two anonymous local lambdas is indistinguishable from a bug. Ask of every predicate in a page/route module: *does a model class already own these fields, and would a reader know which of the two is authoritative?*

- **A name states the component's FUNCTION or ROLE — flag any identifier whose distinguishing word describes the interface shape instead.** The maintainer killed a proposed repo purely on its name, 2026-08-31: *"I don't like `<name>-api` because API is \"interface\", doesn't describe the function or role of the component. Suggest something else."* The test is **"could I delete this word and lose nothing?"** — every networked component has an API, so `-api` carves out nothing. Words that usually fail the test: `api`, `service`, `manager`, `handler`, `util`, `data`, `core`, `common`, `helper`, `wrapper`. Words that pass name a domain noun or the verb the component performs. Apply to modules, route groups, tables, classes and files, not just top-level names; flag it as a MED when a diff introduces such an identifier and a descriptive alternative is obvious from the body. The same message also asked which of two already-descriptive names was better and picked the **more precise** one (`-ml` over `-ai`, because "AI" is a superset that would also cover rule-based systems) — when the maintainer asks "which is better, X or Y," they are asking which is more precise, not which reads better. Sits with the runtime-contract-wider-than-the-name rule above and the no-thin-pass-through-wrapper rule (§H.5).
- **The repo is PUBLIC — committed prose must not name the maintainer as a person or cross-reference their other projects.** Flag any `.md`, JSDoc, or doc-comment line in a diff that says "<Name>", "per <Name>", or justifies a choice by pointing at a sibling project of theirs ("same stack as <other project>"). The maintainer, 2026-09-01, on their first contributor-facing repo: *"remove all mentions about budget and [the other project]. Remove mentions about me. Keeping the user story is okay. Just don't use my name."* The user story is fine — write it as "the user." **The discriminator is prose vs. identifier:** a URL or `owner/repo` slug a contributor actually needs (`git clone https://github.com/hoiekim/<repo>.git`, "open a PR against `hoiekim/<repo>`", a demo link, a contact address) is allowed and already ships in the README; a sentence that names them, or that leaks the existence of their other work, is not. This is the docs-and-PR-body sibling of the comment-hygiene attribution ban and of the PII-in-comments rule above — same never-in-public surface, different content class.
- **Prefer cloning the in-house primitive (budget's or a sibling project's) over an external dependency** — when a diff adds an npm package for something either repo already hand-rolled, flag it. The maintainer, on another project's PR: *"Can we clone the idb client we wrote from scratch in budget app instead of using an external library?"* The two repos deliberately keep their primitives mirrored (cache accessor, Table layer, test harness); a new external dep that duplicates an in-house primitive forks the mental model across both apps and adds supply-chain surface. Before approving any new `package.json` dependency, grep the sibling repo for an existing hand-rolled equivalent. Genuine carve-out: a nontrivial thing neither repo has built (crypto, a parser spec).
- **An alarm-suppression branch is reviewed on THREE axes — who PRODUCED the error, what else the `return` skips, and whether the match is keyed on the condition or on one producer's vocabulary.** Flag any diff that adds or extends a message/substring filter at an alarm-reporting boundary (a `sendAlarm` call site, `POST /api/client-error`, an `error` / `tlsClientError` handler on a listener). **(a) Producer.** An error emitted by *our own code or our own users* must page — The maintainer closed a PR in another project with *"Close this. I want the error to page"* (2026-07-07), and its issue two seconds later with no comment of its own — the quote is on the PR, not the issue. An error emitted by an *anonymous third party* against an internet-facing port is not ours and may be suppressed — the maintainer themself merged a PR in another project (2026-03-28) to silence bare TCP probes on 465. **The discriminator is who produced the error, not whether the code is an alarm boundary**; a rule that stops at "it's a denylist" both blocks the legitimate case and gets ignored when it does. **(b) What the `return` skips.** `if (benign) return;` placed ABOVE `logger.error` suppresses the *evidence*, not just the page: a real failure hiding in that bucket leaves no server-side trace at all, so the next investigation greps the logs and finds nothing. Another project's `src/server/lib/smtp.ts` shipped exactly that shape for **twelve** allowlist entries until a later PR split it into `logger.warn(...)` then `return`, skipping only `sendAlarm`. MED, and the assertion must count the warns (`warnings.filter(...).length === N`), not merely check `error` was not called. **(c) Key.** A substring match is keyed on the *producer's vocabulary*, so the same condition reached through a second code path re-alarms and the list still reads complete. `smtp.ts`'s entries matched OpenSSL negotiation function names plus `smtp-server` strings — the vocabulary of the STARTTLS *upgrade* path — while port 465's implicit-TLS path (`secure: true`) raises Node's own generic `TLS handshake timeout` for the identical client behaviour (connects, never completes the handshake), so it fired 21 h 09 m 52 s after the list was last certified and pre-empted a whole alarm-triage session. Ask which code paths can raise this condition and require the enumeration, not the author's confidence — the axis/sibling helper audit above applied to an allowlist instead of a helper signature.
- **An identity used as a rate-limit, quota, lockout or audit key must not be settable by the caller — and a hop-count / boolean proxy-trust setting does NOT make it unsettable.** Trace the key to its source in one hop and ask *who can set this?* Flag any `getClientIp`-shaped helper that reads `X-Real-IP` or `X-Forwarded-For` **before** the socket-resolved address: those headers are supplied by whoever sends the request, so the caller picks its own bucket and a per-request rotation turns an N-attempt cap into an unbounded one. A PR in another project measured it on the live login route — fixed header value: 5 allowed / 3 rejected; rotating value: **0 of 8 rejected**, on both header names. **The one-line fix is insufficient and that is the part to flag**, because it looks complete: reverting only the proxy-trust half of that PR while keeping `req.ip` still failed 2 tests including the bypass case, since a hop count (`trust proxy = 1`) trusts whichever peer opened the connection — so a request reaching the app port without passing the proxy still names its own `req.ip`. The peer gate must be an **address predicate** (`["loopback", "uniquelocal"]`), and even then it is not airtight: `proxy-addr` trusts all of `10/8`, `172.16/12`, `192.168/16`, `fc00::/7`, so a second container on the compose bridge or a host process hitting the published port still spoofs — that residual belongs in `docs/` as an operator contract, flagged if the PR claims more. Three collateral checks: (a) a docstring asserting a header *"cannot be spoofed by the client"* is a deployment assumption, not a guarantee — flag it as prose that cannot be verified from inside the tree; (b) **changing proxy trust has a blast radius beyond the bucket** — the same setting governs `req.secure`, which `express-session` consults before setting a `Secure` cookie, so a wrong value is a **silent auth outage** (no `Set-Cookie`, nobody stays logged in), not a degradation, and the PR must pin it behaviourally rather than argue it; (c) each distinct rotated key also retains a limiter `Map` entry until the sweep, so the rotation is unbounded memory too. 🔴 Repo note: this defect is LIVE in budget and has no mitigating layer — `src/server/lib/rate-limit.ts`'s `getClientIp` returns `x-real-ip ?? leftmost x-forwarded-for ?? socketIp ?? "unknown"` with the identical unverifiable docstring, it keys `preSessionShedMessage` for `POST /login` (5/15 min) and `POST /client-error` (12/15 min), and `rate-limit.test.ts:265` asserts the precedence as intended. budget is on `Bun.serve`, so there is no `trust proxy` to tighten and a peer-address gate has to be written. Tracked at budget 854. Any PR touching `rate-limit.ts` should either fix this or say why not.
- **An absent / error / empty response is not a product state — flag any diff that maps one to a fact about the system without a control target.** `404` ⇒ the feature is off, `0 rows` ⇒ it never happened, an omitted JSON key ⇒ disabled, a non-zero exit ⇒ the thing under test is broken: each has at least one other cause (no permission, wrong scope, admin-only field, wrong route) and the response cannot tell them apart. The check is one call: **run the identical request against a target whose answer you already know in the OTHER direction**, and if both answer the same, the response is not measuring the claim. A PR in another project did this and declined to build the check it was about to — GitHub's secret-scanning alerts endpoint returns `404` for `cli/cli`, `github/docs` and `octocat/Hello-World` alike, because it needs administrator access that no OAuth scope confers, so `404` reports the caller's access and never the setting. Require **three** verdicts where a diff offers two — *in force* / *drifted* / *not readable with this token* — and flag the collapse of the third into either of the first two. Two corollaries: a **fixture must emit a status the live API actually returns** (the suite that PR replaced manufactured a `403` the endpoint never emits, validating a mapping the API contradicts), and an **unknown verdict belongs in the report, not in the exit code**, unless the PR shows the success exit is still reachable — that PR measured that a reserved "unknown" exit would hold forever and make the close-the-tracker consumer dead code.
