# §F.postgres — Postgres / Table / migrations / SQL engines

Load when the diff touches `src/server/lib/postgres/**` (models, repositories, database.ts), transfer/suggestion DETECTION-engine SQL, or any migration/DDL surface.

- **Transfer DETECTION-engine semantics** (`compute-tools/detect-transfers.ts`, PR #541) — distinct from the calc-exclusion rule above; these govern which candidate pairs the engine proposes. Flag a PR that violates any: (1) **same-`account_id` pairs are never transfers** — a same-account candidate is a bug ("conceptually, same account pair is never a transfer"); (2) **hidden accounts (`account.hide = TRUE`) are HARD-EXCLUDED from candidates**, not tiebroken — the WHERE must carry `COALESCE(a.hide, FALSE) = FALSE` on both join sides (the maintainer chose hard-exclusion "v2" over a tiebreak "v1"); (3) **no manual-label-aware logic in detection** — `category='Transfers'` user labels are eval ground-truth only, never an engine input (the maintainer will drop manual labeling); (4) **rejection uses the `status` column (`status='rejected'`), NOT `is_deleted`** — `getTransferPairs` must filter `status <> 'rejected'`, `pairTransactions` ON CONFLICT must un-reject on manual re-pair, the engine must carry a denylist `NOT EXISTS` so rejected pairs are never re-suggested, and the DELETE /transfers route is a reject (`rejectTransferRoute`); (5) amount match is `t1.amount + t2.amount = 0 AND t1.amount <> 0`, date window is `DATE_WINDOW_DAYS = 7`.
- **Transfer-pair MUTATION-route invariants** (`pairTransactions` / `confirmTransferPair`, PR #547) — distinct from the detection-engine rules above; these govern the manual pair/confirm routes. The hard invariant is **one active pair per transaction**. Flag a PR that violates any: (1) both routes must run a **collision pre-check inside a DB transaction** — reject (return an error, surfaced via `window.alert`) if either txn is already in another active confirmed pair; (2) on success they must **clean up any OTHER active *suggested* pair containing either txn**, scoped to `status='suggested'` and excluding the just-created `pair_id`; (3) 🔴 **that cleanup sets `status='rejected'`, NOT `is_deleted=TRUE`** — superseding a suggestion is USER intent (engine must never re-suggest it), `is_deleted` is the SYSTEM cascade the engine CAN re-suggest from. A cleanup UPDATE doing `SET is_deleted=TRUE` on superseded suggestions is a real bug (the maintainer: *"the previously suggested pairs should be rejected instead of deleted — consistent with transaction labeling"*); (4) concurrency: per-user `pg_advisory_xact_lock` on both routes AND the engine path (#552), existence check uses `FOR SHARE` to serialize against `deleteTransactions`'s EXCLUSIVE lock (#553); (5) the same-`(a,b)` carve-out (ON CONFLICT un-reject from #541) must survive the new cleanup.
- **Suggestion engine: identity features are amount-SIGN-gated** — in `auto-suggest.ts` SCORE_EXPR, the three identity-strength features (`merchant_name` w=100, `name` w=50, `plaid_pfc_primary` w=10) must only fire when the candidate and target share the same amount sign: `(SIGN($target::numeric) = 0 OR SIGN(t.amount) = SIGN($target::numeric))` (the `SIGN($target)=0 OR …` arm keeps a 0-amount target sign-agnostic). Rationale: same merchant + opposite sign is very likely a DIFFERENT category — a −$50 refund must not inherit the +$50 purchase's accepted category by scoring 150 on merchant+name. The amount-band feature is already sign-preserving (lo/hi via Math.min/Math.max); the weak tiebreakers (channel/account/day) stay unguarded. Flag a diff that adds a new identity-strength feature WITHOUT the sign gate, or that drops it. (PR #574, the maintainer 2026-06-28: *"include the amount's sign(+/-) as an important factor. Even if the merchant name is the same if the sign is different it's very likely that the transaction belongs to a different category"*.)
- **Live binding vs eager capture** — when source modules eagerly construct objects from imports (`const pool = new Pool()`), later `mock.module("pg", …)` does NOT retroactively rebind. The pg-FakePool seam (mock `pg` BEFORE the lazy pool is first constructed, as `users.test.ts` does) is the correct workaround. Flag a new test that `mock.module`s the `server`/`client` barrel — that bleeds process-globally across files; mock the leaf `pg` dependency instead.
- **SQL parameter ordering** — when adding/removing a column from an INSERT/UPDATE, every `$N` placeholder downstream shifts. Walk the parameterized values to be sure.
- **Extend `Table.query`, don't bypass it** — when a repo function needs a query shape the existing Table method doesn't expose (date range, custom `orderBy`, `excludeDeleted` override, etc.), the right move is to WIDEN the Table method's options arg, NOT to reach for `buildSelectWithFilters` + `pool.query` directly in the repository layer. Flag any diff that calls `buildSelectWithFilters` / `buildInsert` / `buildUpdate` / `buildUpsert` / `buildSoftDelete` from a repo when a `Table.query`/`.update`/`.upsert` wrapper is one options-arg-widening away from the same shape. This is broader than the "no raw SQL" rule — it also catches the half-step of using the SQL-builder helper directly. Genuine carve-outs (custom aggregates, `pg_trgm similarity()`, composite-PK tables) are fine but want an explicit comment naming what can't be expressed. Copying an existing bypass (`transactions.ts` getTransactions) is NOT a justification — that spreads the anti-pattern. This recurs hard: the maintainer, PR #522, *"I always tell you to prefer to extend the table methods… and you always choose the other way."* **2026-07-07 recurrence (budget PR #598 v3):** `remapSecurityReferences` in `postgres/repositories/securities.ts` originally hand-rolled `UPDATE {tbl} SET security_id = $1, updated = CURRENT_TIMESTAMP WHERE security_id = $2` through raw `client.query` × 4 (one per referring column). The correct shape is `Table.bulkUpdateByColumn(column, columnValue, data, client?)` — mirrors the existing `bulkSoftDeleteByColumn` family, auto-bumps `updated = CURRENT_TIMESTAMP`, accepts the transaction client. Cross-row rewrite by a non-PK column IS a Table extension case (`Table.update(pk, data)` targets single-row-by-PK; the `bulkSoftDeleteByColumn` sibling tells you the abstraction covers N-row-by-column mutation, the update sibling just hadn't landed yet). Flag any hand-rolled `UPDATE ... WHERE {col} = $N` in a repo when a `bulkUpdateByColumn` call is one line. **The `updated = CURRENT_TIMESTAMP` bump ISN'T optional** — budget's `/api/transactions` and `/api/snapshots` are delta-fetched (`WHERE updated >= cursor`), so any UPDATE that skips it breaks FE-cache consistency until the next full sync (logout/login). Table methods encode this invariant; hand-rolled SQL doesn't unless the author remembers.
- **Indexes match access patterns** — when a diff adds a query that filters by a column, check `models/<table>.ts` for an index on that column. If the table grows linearly with users (`transactions`, `transaction_pairs`, `mails`, `holdings`, etc.) and the filter column isn't indexed, the index must land in the same PR.
- **Constraint-adding migration needs an orphan/violation check first + a not-already-present check** — when a PR adds an FK / UNIQUE / CHECK / NOT NULL enforced at migration time (these auto-run on deploy in this codebase), flag MED unless the PR body shows: (a) the constraint isn't already declared on the model / present in `pg_constraint` (the "gap" may already be closed — budget #550 was a no-op because the FK already existed), and (b) a prod-clone violation count of 0 (a single violating row aborts the whole deploy and rolls it back). Note an FK enforces row EXISTENCE only — it does NOT cover soft-deleted (`is_deleted=TRUE`) rows, so an app-layer `AND is_deleted=FALSE` check is still required where a soft-delete race matters; FK + app-check are not redundant. (The maintainer 2026-06-24 "do orphan check first.")
- **Account snapshots are ONE-PER-DAY (`${account_id}-${YYYYMMDD}`) — any user-facing date-edit surface MUST guard collisions before the write.** Flag HIGH: an editable snapshot-date control that lets the user move a snapshot onto a day another snapshot already occupies will make the POST derive the OTHER row's id → server upsert + cache `dict.set` **silently overwrite** it, and the original row's stale-id delete then drops it — one row vanishes with no warning. Correct shape: a `hasDateCollision(accountSnapshots, targetDate, excludeId)` check that aborts the save (before any server call) with an inline error. Same one-per-day family: on a date edit the old-id row must be evicted from cache ONLY after the server confirms its DELETE (a swallowed `.catch(console.error)` on the delete resurrects the row on the next cold sync). budget #632 (2026-07-11). See section J item 5 (management-surface-over-heuristic).
- **A route named/commented "upsert" that calls `Table.update` cannot create — and `noChangeResult` (304) is NOT an error, so it returns `status: "success"` having written nothing.** Flag HIGH any create-capable route whose repository helper uses `accountsTable.update(...)`-style UPDATE-only primitives, and any route guard shaped `if (!result || result.status >= 400) throw` that treats a 304 no-change result as success — especially when the returned id is echoed from the *request* rather than read from a written row, which hides the no-op from every caller. budget #668 (2026-07-31): `POST /api/account` (the only manual-account creation affordance) wrote nothing, returned success, and the client optimistically rendered + IndexedDB-cached an account that vanished on reload; `upsertAccounts` already existed one function above the one the route called. Same family as the already-fixed #572. Ask of every write route: *can the id in this request not exist yet, and if so does this path INSERT?*
- **A jsonb write rewrites the WHOLE document — flag any partial-update path that isn't read-modify-write, and require a sibling-fields-survive test.** Every UPDATE to a jsonb column (`budgets.capacities` is the live one) replaces the entire document; code that "writes the field it cares about" silently clobbers the siblings. The maintainer's standing pre-merge bar (budget 433): *"The jsonb column is vulnerable because every update or write affects all fields in the json. Is our write path safe for this? Do we have enough unit testing to cover it?"* Trace the write end-to-end, confirm it merges into the current document, and require a unit test that updates one field and asserts every other field unchanged. The safest jsonb write is one that doesn't persist a contested value at all (derive-on-read, §J.8).
- **One-time legacy-state cleanup never ships in a production code path — flag any `DO $$` fixup block in `initialize.ts`, any self-healing scrub added to an engine/sync/startup step, and any data-repair script bundled into a behavioral PR.** The smell test: after the cleanup clears its N legacy rows, will any NEW row ever match its WHERE clause? No → it's a one-off the maintainer runs manually; it does not get committed to a path that runs forever (the maintainer, budget 552: *"I don't want you to push a temporary clean up code to prod. This is a recurring instruction"*; another project: *"Don't permanently insert a one-off backfill code. I'll run this backfill manually"*). Yes — the condition is ongoing (e.g. rows newly soft-deleted every sync) → inline is fine. A repair script inside a fix PR is additionally suspect because the damaged state may already be repaired — *"Remove the fix script from 715. I already handled that"* — the PR body must state the assumption so the maintainer can say "already done" before review, and the repair ships as its own artifact, never as a file in the behavioral diff.
- **Every read derives its row set from the session user and every write proves ownership of caller-supplied ids — flag HIGH any route/repo path where a body-sourced id reaches a write, or a table-wide read ships rows, without `user_id = $session` or an ownership join.** The maintainer on a securities fetch returning the whole table (budget 425): *"Does this return all securities in DB? Isn't that unnecessary and vulnerable? Shouldn't we return securities under that user scope only?"* The live worst case: budget 729/733 — `POST /api/snapshot`'s create branch minted `snapshot_id` AND `holding_id` from a caller-supplied `account_id` with no ownership check; one request from an attacker owning zero accounts re-owned the victim's snapshot and live holdings row (CRITICAL cross-tenant IDOR), while the route's update branch looked safe and was the branch everyone cited. Ask of every touched read: where is the user scope? Of every write: can the id in this request belong to another user, and which statement refuses it? "The FE only sends its own ids" is never an answer; "returns everything and the FE filters" fails on both axes (wire cost + exposure).
- **A "most relevant wins" lookup needs its tiebreaker encoded in the ORDER BY, not left to row order.** Primary ordering plus explicit tiebreak (`ORDER BY snapshot_date DESC, source_rank ASC`) — budget 349: *"The most relevant date should always win. However if both security and holding have the same timestamp, then security wins."* Flag a best-match query (price-as-of-date, latest-valid-record, freshest-snapshot) whose ties fall through to insertion order — that's non-reproducible — unless a UNIQUE constraint on the ordering key proves ties impossible, stated in the PR.

- **An upsert on a "make sure this exists" path must not carry a USER-MUTABLE column onto its `ON CONFLICT` clause — it silently reverts the user on every run, and the fallback literal is what ships.** `buildUpsert` (`postgres/database.ts`) emits `ON CONFLICT (pk) DO UPDATE SET …` for every column the INSERT wrote, so a seed/ensure/initialize function that always supplies a value re-asserts it at every boot. A PR in another project (merged 2026-09-16): `initializeAdminUser()` upserted `password: ADMIN_PASSWORD || "<default>"` onto the row it had just read, so (a) a password set through the real reset route `POST /api/users/set-info` reverted at the next restart with no signal, and (b) with `ADMIN_PASSWORD` unset the value re-asserted every boot was the literal `<default>` published in `.env.example`. Flag any upsert inside an `initialize*` / `seed*` / `ensure*` function whose value expression is `ENV || "literal"` — the literal is a production credential path, not a dev default. Correct shape: supply the column **only when creating**, by passing `undefined` so it leaves the statement entirely (do not guard with an `if` at the call site — the column must not reach the builder); if removing the rewrite removes a real capability, bring it back as an explicit opt-in env (`ADMIN_PASSWORD_RESET=1`) that warns it re-applies until removed, and refuse the reset when the source value is empty rather than installing the published default. Require: the decision extracted as a pure function tested as a decision table, an assertion on the payload handed to the repository (not an intermediate), a mutation check naming which cases go red, and every doc stating the old invariant moved in the same commit. Ask of each column in the seed: *can a user change this after first run?* — if yes it is INSERT-only.

- **A full UNIQUE constraint covers soft-deleted rows — any new soft-delete path on such a table needs every INSERT into it to revive on conflict.** Flag HIGH when a diff soft-deletes rows of a table whose UNIQUE has no `WHERE is_deleted = false` (`recurrings_user_merchant_direction_unique`, transfer pairs) while a reconcile step reads with `excludeDeleted: true` and then plain-`INSERT`s. The deleted row is invisible to the lookup, the INSERT raises 23505, and inside a per-user transaction the whole user's run rolls back every tick with one log line. `createRecurring` shows the right shape (`ON CONFLICT … DO UPDATE SET is_deleted = FALSE`). Caught on budget PR 956 R1 (a "withdraw stale suggestions" step); the same latent hole exists on main via stale cleanup (budget#957). The revive itself has three traps (budget PR 959, four review rounds):
  - **Never reset `status`**: a soft-deleted *dismissed* row is the denylist, and reviving it as `suggested` re-suggests what the user refused.
  - **A revived *confirmed* row must skip charges another active recurring holds**, as the attach path does. Only filter there, though: filtering suggestions gets undone by the suggested-refresh branch one run later, which compares against the unfiltered group.
  - **Read `existing` on the transaction's client**, or rows the same-run cleanup just soft-deleted still look active.
- **A fake-`pg` test must honor the WHERE predicate its assertion depends on.** If the fake returns every row for any `SELECT … FROM <table>`, flipping `excludeDeleted` (or any filter) stays green. Require the fake to apply the soft-delete condition when the SQL carries it, and mutation-check the option flip.

- **F-postgres-pool-error-listener — every `pg` `Pool` (and any long-lived dedicated `Client`) needs an `"error"` listener; flag a missing one HIGH.** pg reports a dropped idle connection (a Postgres restart, `pg_terminate_backend`, 57P01) by emitting `error` on the pool. With no listener, Bun 1.4.4 (prod `oven/bun:1`) turns it into an `uncaughtException`, and `start.ts` exits on that, so a DB restart becomes an app crash. Prod hit this 2026-10-22, fixed in budget PR 976. **E2E caveat:** Bun 1.4.0 silently drops the unhandled emit, so a local control on that version "passes" on the broken code. Verify on the prod Bun version. A pool-level listener alone is NOT enough. pg-pool detaches its listener from a client while it is checked out, so a connection killed mid-`withTransaction` or mid-query still emits an unhandled client `error`. Each client needs its own listener, attached on `pool.on("connect")` (`logDroppedConnections` in `postgres/client.ts`, called from `start.ts`). R1 on PR 976 caught a pool-only fix. Don't register the listeners in `getPool()` (test `FakePool`s lack `.on`) or in `initializePostgres()` (its retry recursion stacks listeners).
